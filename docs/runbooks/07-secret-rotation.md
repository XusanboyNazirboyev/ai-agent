# 07 — Rotate a secret

Rule first: never print or paste a secret value (chat, tickets, logs, commits). Confirm only that a variable name is present. A secret that was shown anywhere it should not have been is treated as leaked and rotated.

Where secrets live today: `/opt/tezda/deploy/.env.production` on the host (generated by `bootstrap-staging.sh`, kept across deploys, file mode 600) and encrypted rows in the database (channel tokens, connector secrets, sealed with `SECRETS_MASTER_KEY`). Moving them to a managed store is roadmap P0.3.

| Secret | Where | How to rotate |
|---|---|---|
| `SECRETS_MASTER_KEY` (+ `SECRETS_KEY_ID`, `SECRETS_PREVIOUS_KEYS`) | `.env.production` | see A |
| `WEB_PROXY_SECRET` | `.env.production` | replace with `openssl rand -hex 32`, `dc up -d api web` (both read it) |
| `POSTGRES_PASSWORD` | `.env.production` and inside Postgres | change the role password in Postgres first, then the file, then `dc up -d api`; do both in one maintenance window |
| LLM provider keys | `.env.production` | issue a new key at the vendor, replace, `dc up -d api`, then revoke the old key at the vendor |
| Telegram bot token | encrypted in the database | revoke at BotFather, then reconnect the bot in Channels (the web app stores the new token) |
| Instagram or Messenger token | encrypted in the database | reconnect the account in Channels |
| Bitrix24 incoming webhook | encrypted in the database | create a new webhook in Bitrix24, paste it in Settings, CRM, delete the old webhook in Bitrix24 |
| Operator or admin password | database (hash) | the person changes it in Security; that revokes their sessions |
| Platform admin lost access | database | `ops:platform-admin-reset-mfa` on the server (audited, ADR 048) |
| `jev` MCP key | developer machine, not the host | only the owner can rotate it at the vendor; it was exposed and is still pending |

## A. Rotate `SECRETS_MASTER_KEY`
1. Take a database dump first (06 intro) and copy the current key somewhere safe and separate (a password manager), because losing it makes stored tokens unreadable.
2. Generate the new key: `openssl rand -base64 32` (do not echo it into a log).
3. In `.env.production`: set `SECRETS_PREVIOUS_KEYS=<old id>:<old key base64>` (comma separated for several), set `SECRETS_MASTER_KEY=<new key>` and `SECRETS_KEY_ID=<new id>` (letters, digits, `_` or `-`, up to 40).
4. `dc up -d api`. New secrets are sealed with the new key; old ones are still read through the previous key (the keyring in `secrets/secret-cipher.ts`).
5. Verify that a channel and the CRM connector still work (send a test message; the roles block shows `BOUND`).
6. Old keys stay in `SECRETS_PREVIOUS_KEYS` until every stored secret has been re-sealed. **There is no re-encryption tool yet**: reconnecting a channel or connector re-saves its secret under the new key. Do not delete an old key while any stored secret may still use it. Writing that tool is an open item.
