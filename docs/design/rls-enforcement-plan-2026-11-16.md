# RLS enforcement plan (P0.7 follow-up to ADR 050), 2026-11-16

Architect design; slices S1 and S2 built on 2026-11-16 (see Status). Today the policies exist (ENABLE, not FORCE) but the app connects as the table owner and sets no tenant context (`PrismaService.withTenant` is used nowhere), so nothing is enforced. Switching to a restricted role now would make every protected query return no rows.

## Design
- **Context:** `persistence/tenant-context.ts` (AsyncLocalStorage, set once, immutable). HTTP: the slot opened in `observability/trace-requests.ts`, filled by `SessionGuard` (same pattern as `observability/log-context.ts`). Jobs: `runWithTenant(data.tenantId)` in `telegram-queue.runtime.ts` and `connectors/sync/catalog-sync.queue.ts`.
- **Applying it:** a wrapper around the PrismaPg driver adapter (`SqlDriverAdapter` / `Transaction`, `@prisma/driver-adapter-utils@7.10.0`): `startTransaction()` runs `set_config('app.tenant_id', $1, true)` first; a standalone query runs in BEGIN, set, query, COMMIT. Cost: +1 round trip per interactive transaction, 4 instead of 1 for a single query (local Docker DB, about 1 ms). Rejected: one transaction per request (holds a pool connection through LLM calls; pool is 10). Unverified until slice S2 proves it: that AsyncLocalStorage reaches the adapter calls in Prisma 7.10.
- **Privileged client:** `PrivilegedPrismaService` via `createPostgresAdapter(env, 'POSTGRES_ADMIN_')` for sign-in and session lookups, MFA, invite acceptance, webhook routing to a tenant, outbox publishing, the inbox event bus poller, the scheduled scans (find tenants, then per-tenant context), `platform/**`, `ops/**`, `dev/**`, scripts and migrations. A unit test allows injecting it only in those files.
- **Failing loudly:** `RLS_CONTEXT_MODE` = off | warn | strict; strict throws on a protected query without a tenant. A CI job runs the integration suite as a NOBYPASSRLS role in strict mode.

## Slices
S1 context, S2 adapter wrapper plus tests as a NOBYPASSRLS role (interactive transactions, single queries, raw SQL, nested writes), S3 privileged client, S4 HTTP slot and guard, S5 pre-tenant lookups, S6 queues, S7 scans and event bus, S8 strict CI job, S9 policies on the remaining tenant tables by domain, S10 staging: warn mode on the owner role, then switch to the app role.

## Owner steps (only at S10)
Approve creating `agentcore_app` (LOGIN, NOSUPERUSER, NOBYPASSRLS; DML grants, default privileges, no access to `_prisma_migrations`) with a new secret; a verified backup; the switch of `POSTGRES_USER`/`POSTGRES_PASSWORD` to that role while migrations and the privileged client keep the owner role (`POSTGRES_ADMIN_*`). Rollback: point `POSTGRES_USER` back and restart; dropping the role needs separate approval.

## Risks
Two pools per process (check `max_connections`); session-level advisory locks or `SET` in raw SQL that the wrapper would move into a transaction (`handover/conversation-lock.ts`, `agent/llm-budget-ledger.ts`); the inbox event bus `setInterval` inherits the first subscriber's context (`webinbox/inbox-event-bus.ts`); triggers run as the caller (`leads_fill_pipeline_trg` reads `pipelines`); 195 raw SQL or transaction sites in 66 files, `webinbox/analytics.service.ts` the largest; missing context fails closed as silently empty results, so strict mode in CI and alerts on warn logs.

## Status
- **S1 done:** `apps/api/src/persistence/tenant-context.ts` (`runWithTenant`, `runWithTenantSlot`, `setTenant`, `runWithoutTenant`, `currentTenant`). HTTP requests open a slot in `observability/trace-requests.ts`; `SessionGuard` fills it. Jobs and scans do not set it yet (S6, S7).
- **S2 done:** `persistence/tenant-adapter.ts` wraps the PostgreSQL adapter; `PrismaService` uses it with `RLS_CONTEXT_MODE` (default `off`: the plain adapter, no change in behaviour). Verified in `tenant-adapter.integration.spec.ts` on a probe table with FORCE RLS (the test database user may not create roles, so a NOBYPASSRLS login role is left to S8 in CI): single statements, interactive transactions, raw SQL, nested writes, 20 concurrent operations of two tenants, strict refusal and warn reporting. Mutations: dropping the setting from single statements or from transactions each fail 2 tests.
- **Findings while building:** (1) adapter-pg 7.10 `Transaction.commit()` only releases the connection; COMMIT and ROLLBACK are statements sent by the client, so the wrapper sends them for its own short transactions. (2) Prisma queries are lazy thenables: `runWithTenant(id, () => prisma.x.findMany())` returned unstarted would run outside the context when awaited; `runWithTenant` therefore starts a returned thenable inside the context. Code inside an async callback is unaffected.
- **S3 done:** `persistence/privileged-database.ts` (`PrivilegedDatabase.db`). With `POSTGRES_ADMIN_USER` unset it is the main `PrismaService` (no extra pool); set, its own pool as that role, never wrapped with the tenant context. `privileged-database.spec.ts` keeps an allowlist of files that may use it (only persistence today; S5 to S7 add each cross-tenant user with a reason).
- **S5 done (2026-11-16, `feat/ui-words-menu`).** Callers found with a temporary warn-mode trace of the API integration suite (not committed). What changed:
  - *Identity, cross-tenant by nature* -> `PrivilegedDatabase` for the whole service: `webinbox/session.service.ts` (login by e-mail, `resolve` by cookie hash, MFA login, failure counter), `auth/mfa.service.ts` and `auth/mfa-store.ts` (challenges, enable/disable/reset/regenerate). Invites: `team/operator-invite.service.ts` finds the invite by its token on the privileged connection (`preview`, `accept`), then runs the accept transaction under `runWithTenant(invite.tenantId)`. Tables: operators, operator_credentials, operator_sessions, mfa_challenges, operator_invites (no RLS policies; whether they ever get one is decided in S9).
  - *Tenant known, work for that tenant* -> `access/tenant-access.service.ts` reads tenants and tenant_subscriptions under `runWithTenant(tenantId)`; a tenant id that is not a UUID is reported ARCHIVED without a query.
  - *Webhook routing* -> one lookup on the privileged connection finds the account's tenant, everything else runs under it. Telegram: `TelegramWebhookService.routeTenant` (by account id, any status), and the controller handles the whole update (secret, operator group, group link, intake) inside `runWithTenant`; an unknown account answers 503 "not configured" before the secret check. Instagram and Facebook: `InstagramWebhookService` routes each event by `(channelType, externalAccountId)` (unique) and runs `accept`, `acceptPostback` and `acceptComment` under the tenant; the in-transaction channel lookups also filter by that tenant.
  - Services take `PrivilegedDatabase` as an optional last constructor argument and fall back to `PrismaService` only when a spec builds them by hand; under Nest both come from `PersistenceModule` (asserted in `privileged-database.spec.ts`, whose allowlist now names each user with its reason and fails on stale entries).
  - `RLS_CONTEXT_MODE=strict` now requires `POSTGRES_ADMIN_USER` (environment validation).
  - Warn mode reports every statement run on the main connection while a request is still waiting for its tenant (`awaitingTenant()`, `inRequest: true`); other misses stay sampled.
  - *Behind `SessionGuard` yet without a tenant* (TeamController, LeadPipelineController and 11 more in the trace): all from specs that call controllers directly, without the request slot `main.ts` opens (`traceRequests`), so `setTenant` has nowhere to write. No production change; S8 (spec harness).
  - **Verified:** `persistence/rls-http-context.integration.spec.ts` boots the real AppModule with the request slot, warn mode and a separate privileged pool, then signs in, reads `/auth/me`, `/team`, `/inbox/conversations`, creates and accepts an invite, and posts a Telegram and an Instagram webhook: zero in-request statements without a tenant. Mutations: the session service or the Instagram routing back on the main connection fail it (2 and 1 tests). API typecheck, lint, format and integration (877/877) pass; API unit 2841 pass with one local-only failure that also fails without these changes (the live-eval CLI guard reads the local `.env`; green in CI). The catalog-sync BullMQ integration test failed twice locally (also without these changes) and passed in the final run.
  - **Not yet:** the app cannot boot in strict mode: `PrismaService.onModuleInit` (`assertUtcSession`) and other startup hooks and jobs have no tenant (S6/S7). *Platform console* (`platform/**`, cross-tenant admin) is S5b. *Jobs and scans* (catalog sync, outbox, `TelegramAgentPipeline.run`, `LeadSyncService.record`) stay S6/S7; spec fixtures and controller-direct specs stay S8.
- **Next:** S5b (platform console on the privileged connection), then S6 and S7 (queues, scans, the event bus, startup checks), S8 strict CI job as a NOBYPASSRLS role.
