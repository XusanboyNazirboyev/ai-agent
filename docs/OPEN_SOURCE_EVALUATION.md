## Cross-cutting findings

- **Webhook intake:** Telegram's Bot API specifies an HTTPS POST containing an `Update`, the `X-Telegram-Bot-Api-Secret-Token` header when `secret_token` was configured, retries when the response is not 2xx, and `update_id` as the update identity useful for duplicate suppression and restoring update order. These are the protocol details Phase 2 follows. [Telegram Bot API: webhooks and Update](https://core.telegram.org/bots/api#update).
- **Queue and order:** Dify and n8n show mature worker separation; LangGraph shows resumable state; none changes the need for AgentCore's durable inbox/outbox, provider-scoped unique keys, and database-enforced conversation serialization. A queue's FIFO behavior alone is insufficient once concurrent workers, retries, and process restarts are involved.
- **CRM and handover:** Integration/connector interfaces and Botpress's HITL port are useful boundaries. They do not prove any specific CRM API, authorization model, tenant isolation, or exactly-once effect. AgentCore must retain the canonical CRM connector contract and handover state machine from its own specification.
- **Operational and maintenance review:** All five projects have active official documentation/repositories, but activity is not a support guarantee. Before adopting any component later, pin a release, review supported runtime/database/Redis versions, inspect security advisories and transitive dependencies, and assign upgrade ownership. Botpress Cloud and Dify are full platforms; Rasa and LangGraph introduce Python services; n8n is a substantial workflow service with license and worker-topology implications.

## Recommendation

Keep the current NestJS + PostgreSQL/Prisma + Redis/BullMQ architecture. Adopt patterns, not a second platform: typed channel adapters; authenticated bounded webhooks; a transactional outbox; durable idempotency keys; explicit per-conversation locking; bounded retries with exhausted-job visibility; and a human-intervention interface that remains independent of the channel. The Phase 2 implementation uses BullMQ because it is already in the project specification and Redis foundation; none of the five evaluated products is installed or deployed.

Possible later evaluation: a TypeScript graph library only after Phase 4 requirements show that a graph adds value beyond the planned code-controlled slot/tool loop; a workflow service only for internal operations after license and data-flow review. Do not adopt Botpress, Rasa, Dify, or n8n as AgentCore's core engine or install them as dependencies for Phase 2.

## Phase 3 note (2026-10-23)

The connector framework (registry, mock and generic REST connectors, conformance suite, sync core) was built without adopting any of the five projects; none is installed. It follows AgentCore's own contract (AGENTS.md §5.2, [ADR 006](adr/006-connector-outbound-security-and-contract.md)). The reference patterns noted above still apply: integration contracts separated from the core (Botpress) and a credential/execution plane kept outside tenant data (n8n). This session made no new external claims about these projects and did not re-verify their licenses or repositories; re-check them before any later adoption decision.
