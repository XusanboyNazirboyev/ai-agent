# Load test, 2026-11-18 (local, mock model)

Pilot plan step 5 asks for "a short load test"; spec 09 for a load test before launch. This is the first one. Harness: `apps/api/src/testing/load/telegram-load.load.ts`, run with `LOAD_TEST=1 pnpm --filter @agentcore/api test:load` (settings in the file header).

## Set-up
- **Code:** commit `cfc5ece` plus the queue-concurrency setting from the same day.
- **Machine:** one MacBook (darwin), Node 26, local PostgreSQL (Postgres.app) and Redis. The real AppModule runs in one process against `agentcore_test`.
- **Tenant:** a fresh fictional tenant (education pack, mock catalog connector) with a LIVE Telegram account.
- **Model:** `LLM_PROVIDER=mock`. One series uses no delay. The other adds 1.5 s to every model call, close to a fast hosted model; a turn makes two calls.
- **Telegram:** answered in process (global `fetch` replaced before boot; any other outbound host is refused). Nothing left the machine and nothing cost money.
- **Customers:** stages of 5, 20 and 50 customers at once. Each sends 4 messages one by one, the next 200 ms after the bot's reply.
- **Reply time:** from the webhook request to the bot's first `sendMessage` to that chat. It includes the 2 s inbound debounce (ADR 005, spec 06: merge rapid messages), so "above debounce" is the rest: queue, turn, guardrail, commit, outbox relay, send.

## Findings
1. **The channel queue saturates at 8 jobs at once.**
   - With a realistic model and 50 customers writing at once, the reply wait doubles to about 12 s. Throughput stays at about 1.5 replies/s.
   - With 24 jobs at once, the same load gets p50 5.8 s and p95 7.0 s.
   - The number was hard-coded. It is now `TELEGRAM_QUEUE_CONCURRENCY` (default 8, unchanged).
   - Order within a conversation does not depend on it: the conversation lock keeps it.
2. **Platform overhead is about 0.8 s at p50** above the debounce, even with an instant model, at every concurrency.
   - **Probable cause (a hypothesis; there are no per-stage timings):** two outbox hops that each poll every 500 ms. The inbound event waits for the relay, then the send event does.
   - **Possible fix:** wake the relay right after a commit. Measure each stage first.
3. **Webhooks stay fast.** Accept p50 is 13–64 ms and p95 at most 571 ms at every stage.
4. **One webhook was not answered 200** in about 1,000 sent over five runs. It happened in the first run with the model delay, before status codes were recorded, so the status is unknown. It did not happen in four later runs (about 620 webhooks) that recorded every status.
   - Telegram is believed to retry an update its webhook did not accept. This is unverified: the Bot API docs were not re-read today.
   - The harness now records the status and body of any rejection.
5. **The silent fourth message is expected.**
   - With the mock model, every customer's third message ends in a handover.
   - The bot then stays silent while the conversation waits for a person (D12). All timeouts are on the fourth message, and every test conversation ends `WAITING_OPERATOR`.
6. **Memory was not measured as a leak test.** The worker process RSS rose from about 315 MiB to 600–1000 MiB per run. A garbage-collected process makes that number noisy.

## Not shown
- The staging instance size, its database connection limit, or its network.
- Real model latency, cost or rate limits.
- Telegram's own limits.
- More than one API process.
- A long soak (all runs were minutes long).
- Packs other than education.
- Voice and media messages.

## Decisions for the owner
- **Staging concurrency:** raise `TELEGRAM_QUEUE_CONCURRENCY` (for example 16–24) or run a second API process. Do it before the pilot is expected to have tens of customers writing at once. Check the model provider's requests-per-minute limit and the database connection limit first.
- **Next tests:** a soak run (30–60 min) and a run against staging. Both use shared resources and need a time window.
