# Known defects

Numbered, so ADRs, the roadmap and commits can refer to them. "Found by" links the evidence.

| # | Area | Defect | Found by | Status / plan |
|---|---|---|---|---|
| DEF-001 | Agent / follow-ups | A price shown through a live quote (`list_offers` then `get_quote`, rendered from fact placeholders) is **not recorded** as a `ShownOffer` or `Quote` row. The follow-up policy requires one (or a warm lead), so **v1 never follows up after answering a price question**. | Slice 1 harness; pinned by `simulation.integration.spec.ts` ("records that v1 sends no follow-up after a quoted price") | **Slice 1b**, after the paid gating baseline is measured (so the baseline stays pure v1): record the shown offer/quote, add a regression test, flip the characterisation test, and add a scenario |
| DEF-002 | Travel pack config | The travel pack has **no `highValue` threshold**, so a large group (scenario `tour-07`, 12 people) cannot hand over as `HIGH_VALUE`. | Slice 1 scenarios | Roadmap: travel pack configuration task (with the owner's threshold) alongside slice 3 |
| DEF-003 | Packs | **No retail pack.** The 10 retail scenarios (30 units) are not runnable on v1 and are reported as "not runnable (pack missing)". | Slice 1 | Roadmap slice 3b (retail pack as configuration, mock-only per decision 3) |
| DEF-004 | Tooling | `pnpm llm:smoke <provider>` **overwrote** `docs/LLM_PROVIDER_STATUS.md` with only the tested providers, deleting other rows and the observations. | Slice 1 (file restored) | **Fixed** on `slice1/scenario-harness`: rows are merged (`mergeStatus`, `smoke-status.spec.ts`) |
| DEF-009 | Web API / tests | **Cross-tenant isolation of the channel connect API is tested for `disable` only.** Every route resolves the account through one helper that filters by the operator's tenant (a foreign id gives `NOT_FOUND`), so the code looks right, but no test has tenant B call `enable`, `test`, `disconnect` or `operator-group` on tenant A's account. Tenant B connecting tenant A's bot is tested (`ALREADY_CONNECTED`). | Review of `feat/web-api` (`telegram-connect.integration.spec.ts`) | OPEN. Add one test per route |
| DEF-010 | Web API / secrets | **Nothing tests that the bot token stays out of log lines and thrown error messages.** By reading the code it does: `TelegramManagement` replaces every failure with a code-only error, the controller logs only `telegram.webhook_not_removed` with the account id, and the response, audit rows and stored ciphertext are asserted token-free. But `TelegramManagement` has no unit test, and `telegram()` rethrows unknown errors unchanged. | Review of `feat/web-api` | OPEN. Add a test that captures logs and error messages while Telegram calls fail |
| DEF-011 | Web API / Telegram | **Disconnect can leave the webhook registered at Telegram.** `disconnect` removes the webhook best effort (a failure is only logged) and then deletes the stored token, so after a Telegram outage the webhook stays registered and can only be removed with the bot token elsewhere. Deliveries are still refused (the account is DISABLED and its webhook secret is gone). Tests cover disable then disconnect; disconnect of an ACTIVE account and the failure path are not tested. | Review of `feat/web-api` | OPEN. Decide whether disconnect should fail or retry when the webhook cannot be removed; add both tests |
