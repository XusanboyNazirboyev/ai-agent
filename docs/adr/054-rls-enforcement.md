# ADR 054 — Enforcing Postgres RLS at runtime (P0.7, amends ADR 050)

Status: accepted by the owner on 2026-11-12 (decisions 1 to 3 and 5 below confirmed with "ha"; decision 4 deferred). Stage S0 (this ADR and a measured spike) is in progress; stages S1 to S7 are scheduled before the first real customer's data is stored (staging holds demo data only). Roadmap item P0.7; finding SEC-04 in `docs/audit/2026-11-10/AGENTCORE_SECURITY_AND_PRODUCTION_REVIEW.md`.

## Context (verified from the code on 2026-11-12)
- Eight tables have tenant-isolation policies: `contacts`, `conversations`, `messages`, `leads`, `handovers`, `knowledge_chunks` (migration `20261117090000`), `persons` (`20261118090000`), `person_merges` (`20261119090000`). `contact_identities` is still owed if it is ever created (ADR 050).
- **RLS protects nothing at runtime today.** The application connects as a superuser in CI (`.github/workflows/ci.yml`), staging (`deploy/bootstrap-staging.sh`, `deploy/docker-compose.local-db.yml`) and docker-compose dev; a superuser bypasses RLS. `PrismaService.withTenant` (`apps/api/src/persistence/prisma.service.ts`) has no callers. The only runtime protection is the application-level `tenantId` filter plus tests.
- About 763 Prisma model calls, 79 `$transaction` sites and 51 raw SQL sites in `apps/api/src` (approximate, regex counts; roughly 42 calls are in `testing/` helpers). 38 tenant-owned tables have no RLS yet (the sensitive ones: `channel_secrets`, `connector_secrets`, `operator_credentials`, `operator_sessions`, `operator_api_tokens`, `internal_notes`, `inbound_events`, `outbox_events`, `agent_turns`, `audit_events`).
- Under an enforced role an uncovered SELECT silently returns 0 rows (`NULLIF('')` gives NULL), an INSERT fails the WITH CHECK, an UPDATE/DELETE affects 0 rows. The silent case is the dangerous one.

## Decisions
1. **Three database roles (owner decision 1, confirmed).** The existing owner role stays for migrations (`prisma migrate deploy`), seeds and backups only. New `agentcore_app` (LOGIN, NOSUPERUSER, NOBYPASSRLS, not owner) serves the API and workers. New `agentcore_system` (LOGIN, BYPASSRLS, not owner) serves an explicit allow-list of cross-tenant code. Roles and grants are additive and idempotent; passwords are never in migrations and never committed: they come from the host environment (`.env.production` / SSM) through `deploy/set-db-role-passwords.sh`. New variables `POSTGRES_APP_USER/PASSWORD`, `POSTGRES_SYSTEM_USER/PASSWORD`; when unset the app falls back to `POSTGRES_USER` (current behaviour). This interacts with SEC-05 (secrets to Parameter Store): do them together.
2. **Tenant context (recommended option, accepted).** An `AsyncLocalStorage` `TenantContext` plus a Prisma client extension. Operations on the RLS models run with `set_config('app.tenant_id', <id>, true)` as the first statement of the transaction they run in (a batch transaction when there is none; the first statement of an interactive `$transaction`). Only transaction-local settings (`true`) are allowed, so nothing leaks through the pool; a test asserts the setting is empty on a fresh pooled query and a lint/grep test forbids `set_config(..., false)`. Raw SQL on RLS tables goes through `withTenant` explicitly. Rejected: explicit `withTenant` at every one of ~763 call sites (easy to miss, silent 0 rows); one pinned connection per request (session settings leak across the pool, does not fit BullMQ jobs or SSE).
3. **Fail loudly (owner decision 2, confirmed).** `DB_RLS_MODE=off|warn|strict`. In `strict`, an RLS-model operation with no tenant context and no `asSystem()` throws in code instead of returning nothing. CI runs the integration suite as `agentcore_app` in `strict`. Staging: `warn` for about 48 hours, then `strict`. Production: `strict` (fail closed: a missed path is a 500 or a failed job, never a silent empty result).
4. **System paths (owner decision 3, confirmed).** The platform console (7 controllers under `platform/`) and the cross-tenant scans (follow-up, idle-return, handover SLA scan, retention selection, alerts, subscription scan) use a separate `PrismaSystemService` on its own small pool (about 3 connections) bound to `agentcore_system`. Selection of candidates runs on the system client; the work on each candidate runs with that tenant's context. The allow-list is enforced by an import-boundary test (like the existing platform one). Scripts under `ops/`, `dev/`, `prisma/seed.ts` and `scripts/e2e-fixtures.ts` run as owner or system.
5. **No `FORCE ROW LEVEL SECURITY` (owner decision 5, confirmed).** The owner stays exempt so migrations and `pg_dump` backups keep working.
6. **Scope (owner decision 4, deferred).** This ADR covers the eight tables above. RLS on the secrets, credentials, internal notes and inbound-event tables comes later under its own ADR.

## Stages (each ships alone and reverts by environment variables only)
- **S0 ADR and spike (S):** this ADR; prototype the context and extension; measure the added latency (p50/p95) on the inbox list and the agent turn; check whether query extensions intercept `$queryRaw` with `@prisma/adapter-pg` (not relied on).
- **S1 roles (M):** idempotent migration creating the two NOLOGIN roles with GRANTs and `ALTER DEFAULT PRIVILEGES FOR ROLE <owner>`, the password script, env variables, `.env.production.example` entries. Rollback: unset the variables. On RDS `CREATE ROLE` needs `CREATEROLE` (unverified).
- **S2 plumbing (M):** `TenantContext` set in `SessionGuard`, `OperatorRequestGuard`, after webhook channel resolution (`channel_accounts` has no RLS, so the lookup works), per inbound event and per scan candidate; the extension with `DB_RLS_MODE`; `PrismaSystemService`. Rollback: `DB_RLS_MODE=off`.
- **S3 discovery (S):** non-blocking CI job running the suite as `agentcore_app` in `strict` (migrate and fixtures as owner) to list uncovered paths; EXPLAIN of the pgvector query (`knowledge.service.ts`) as `agentcore_app` (pgvector operators are not LEAKPROOF, the planner may skip the vector index; unverified).
- **S4 fix by area (L, about 5 PRs):** inbox controllers; channels and inbound; schedulers; the raw SQL sites; persons.
- **S5 CI blocking in `strict` (S).**
- **S6 staging (M, owner):** verified backup, create roles and passwords, switch the api env, `warn` 48 hours, then `strict`. Rollback: unset the variables and restart.
- **S7 production (S, owner):** same steps.

## Risks
Per-operation cost (BEGIN, set_config, COMMIT: about 3 extra round trips outside a transaction, each holding a pool connection; pool max is 10): measured in S0, not guessed. Raw SQL on RLS tables outside a transaction needs `withTenant` (about 37 table-touching sites). Default privileges apply to new tables only when the same owner role creates them. `pg_dump` as a non-owner fails on RLS tables: backups stay on the owner, and a restore must create the roles first (or restore with `--no-privileges` and re-run S1). Two pools (10 plus about 3). Long-lived SSE streams must not hold a transaction.

## Verification
S0: spike numbers recorded in this ADR. Each later stage: integration suite as `agentcore_app` in `strict`; cross-tenant read and write attempts return 0 rows or fail; the pooled-connection leak test; the import-boundary test; staging smoke after each switch.
