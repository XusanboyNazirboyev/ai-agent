# ADR 057 — Multiple pipelines and the lead as an opportunity (P1.3)

Status: proposed by the reviewing agent on 2026-11-12 for the owner's review (the owner asked to continue the roadmap in order: P1.1, P1.5, then P1.3); implementation staged below. Roadmap item P1.3 ("Pipelines (multiple) + Lead as opportunity (owner, amount, source, close date, lost reason); two pipelines with own stages; Kanban per pipeline; Bitrix24 sync unchanged"), `docs/audit/2026-11-10/AGENTCORE_DEVELOPMENT_ROADMAP.md`. Depends on P1.1 (done) and builds on P1.5 (`leads.custom_fields`, tags).

## Context (read from the code on 2026-11-12)
- `lead_stages` is one flat, per-tenant list: unique `(tenant_id, code)`, optional `code` (the four defaults `NEW`, `HOT`, `WARM`, `COLD` are created lazily by `ensureLeadStages`), optional `name` for custom stages, `position`. Leads point at it by `pipeline_stage_id` (nullable). Routes: `GET/POST /api/v1/leads/stages`, `PATCH /leads/stages/:id` (rename), `GET /leads` (board list), `PATCH /leads/:id/stage` (`apps/api/src/webinbox/lead-pipeline.controller.ts`).
- A lead is created per conversation by the agent (`conversation_id` is required) and carries `score` (COLD/WARM/HOT), `status` (`NEW | IN_PROGRESS | WON | LOST`), `summary`, collected `requirements`, CRM sync fields. It has no owner, amount, source, close date or lost reason.
- The Bitrix24 lead sink (`lead-sync.service.ts`, ADR 034) does not read the stage, so a pipeline change does not affect it; two-way stage sync is roadmap P2.8 and out of scope here.

## Decisions
1. **A `pipelines` table.** `id` uuid(7), `tenant_id`, `name` varchar(80), `position` int, `is_default` boolean, `created_at`, `archived_at`. Unique `(tenant_id, id)`; exactly one non-archived default per tenant (partial unique index `(tenant_id) WHERE is_default AND archived_at IS NULL`, SQL-only like the tag-name index in ADR 053). Limits: at most 10 active pipelines per tenant, at most 20 stages per pipeline. RLS tenant-isolation policies in the ADR 050 style.
2. **Stages belong to a pipeline.** `lead_stages.pipeline_id` (NOT NULL after the backfill) with a composite FK `(tenant_id, pipeline_id)`; the unique `(tenant_id, code)` becomes unique `(tenant_id, pipeline_id, code)`; `lead_stages` is not given RLS in this ADR (see ADR 054; it joins in the later wider RLS ADR).
3. **A lead belongs to exactly one pipeline.** `leads.pipeline_id` NOT NULL (default: the tenant's default pipeline) and the stage must belong to the same pipeline: composite FK `(tenant_id, pipeline_id, pipeline_stage_id)` to `lead_stages (tenant_id, pipeline_id, id)`; a lead with no stage is allowed and shows in the first column of its pipeline. Moving a lead to a stage of another pipeline changes `pipeline_id` in the same update (one `PATCH /leads/:id/stage` call; audit event records both pipelines).
4. **Migration (expand, backfill, switch, in one migration, additive, no data loss):** create `pipelines`; insert one default pipeline per tenant named `Sales` (localised at read time: the stored name for the default pipeline is `null` and the web shows the i18n label `pipeline.defaultName`); add `lead_stages.pipeline_id`, backfill every stage to its tenant's default pipeline, set NOT NULL, swap the unique; add `leads.pipeline_id`, backfill from the lead's stage or the default pipeline, set NOT NULL, add the composite FK. Idempotent backfill statements; verified counts (stages without pipeline = 0, leads without pipeline = 0) in the integration test. `ensureLeadStages(tx, tenantId)` is changed to ensure the default pipeline and its four default stages and to return the first stage id of the default pipeline.
5. **Opportunity fields on the lead** (all nullable, additive): `owner_operator_id` (FK `(tenant_id, owner_operator_id)` to `operators`, `ON DELETE SET NULL` is not expressible with the composite tenant FK; use `RESTRICT` and clear the owner when an operator is deactivated: add that to the existing deactivation path and test it), `amount` `numeric(14,2)` with `currency` char(3) (ISO 4217, validated against a fixed list in code; both set or both null), `source` varchar(60) (set at creation from the channel type, e.g. `telegram`, `instagram`; editable free text, trimmed), `expected_close_date` date, `lost_reason` varchar(200) (only meaningful with status `LOST`; required when an operator sets `LOST`, cleared when the status leaves `LOST`). Status transitions stay as today; `WON` and `LOST` do not move the stage automatically in this slice.
6. **Money is operator data, never a customer-facing fact.** `amount` is entered by operators for forecasting. The agent, the reply composer, guardrails and rendered facts never read it (AGENTS.md rule 2: price, date, seats come only from validated tool results with provenance). The ADR and a test assert that no module under `apps/api/src/core/agent/` imports the lead amount (a grep-style test).
7. **Owner assignment is not routing.** `owner_operator_id` is a CRM label for the person responsible; it does not change who receives handovers (teams, queues and assignment rules are roadmap P1.8).
8. **Archive, never delete.** `DELETE /api/v1/pipelines/:id` archives; refused with 409 `PIPELINE_HAS_LEADS` while any lead is in it (the response includes the count; the operator moves them first) and with 409 `PIPELINE_IS_DEFAULT` for the default pipeline. The default pipeline can be changed by `POST /pipelines/:id/make-default`. Stages are archived the same way (`archived_at` on `lead_stages`) when they hold leads, hard-deleted only if empty and not a coded default stage; renaming stays as it is.
9. **Backwards compatibility:** every existing route and JSON shape keeps working. `GET /leads/stages` returns the default pipeline's stages unless `?pipelineId=` is given; `GET /leads` takes an optional `pipelineId` (default: the default pipeline); `LeadPipelineItem` gains additive fields (`pipelineId`, `ownerOperatorId`, `owner` `{id, displayName}` or null, `amount` as a decimal string, `currency`, `source`, `expectedCloseDate` as `YYYY-MM-DD`, `lostReason`).

## API (session guard, tenant from the principal, tenant-scoped queries, error shape `{ statusCode, message, code, i18nKey }`)
- `GET /api/v1/pipelines` (any role) -> `{ items: { id, name, position, isDefault, stageCount, leadCount }[] }`, active only. `POST /pipelines` `{ name }`, `PATCH /pipelines/:id` `{ name?, position? }`, `DELETE /pipelines/:id` (archive), `POST /pipelines/:id/make-default`: OWNER and ADMIN only (403 otherwise); codes `PIPELINE_LIMIT`, `PIPELINE_HAS_LEADS`, `PIPELINE_IS_DEFAULT`, `NOT_FOUND`.
- Stages: `GET /leads/stages?pipelineId=`; `POST /leads/stages` gains `pipelineId` (optional, default pipeline); new `PUT /pipelines/:id/stages/order` `{ stageIds }` reorders (must be exactly the active stages of that pipeline, 400 `INVALID_BODY` otherwise); `DELETE /leads/stages/:id` per decision 8 (`STAGE_HAS_LEADS`, `STAGE_IS_DEFAULT`, `STAGE_LIMIT`). Roles as today (managers).
- `PATCH /api/v1/leads/:id/stage` `{ stageId }` as today, now across pipelines.
- `PATCH /api/v1/leads/:id/opportunity` `{ ownerOperatorId?: uuid|null, amount?: string|null, currency?: string|null, source?: string|null, expectedCloseDate?: string|null, lostReason?: string|null }` for OWNER, ADMIN, OPERATOR (VIEWER 403). Validation: amount a decimal string `^\d{1,12}(\.\d{1,2})?$`, strictly the pair with currency; owner must be an active operator of the tenant (400 `UNKNOWN_OPERATOR`); close date a real calendar date; `lostReason` allowed only while status is `LOST` (400 `INVALID_VALUE`). Status changes to `LOST` through the existing status route require `lostReason` (extend that route's body; 400 `LOST_REASON_REQUIRED`).
- Reads: leads list filters `ownerOperatorId`, `source`, `closeBefore`/`closeAfter` (dates), and the existing `stage`, `score`, `tagId`.
- Audit events for pipeline and stage changes, moves between pipelines, and opportunity edits (field names only, no amounts).

## Risks
Migration touches two hot tables (constraint swap): run on staging only after a verified backup, in a quiet window; the backfill is set-based and idempotent. Composite FKs make a wrong-pipeline stage impossible at the database level but need careful Prisma modelling (read how ADR 052 and 053 modelled composite relations). Currency and decimal handling: money crosses JSON as strings, never as JS numbers. The partial unique index for the default pipeline is SQL-only and must keep `pnpm db:test:drift` clean (see ADR 053 for how). Existing web code reads stages as a flat list: the compatibility rule in decision 9 keeps it working until S2.

## Open decisions for the owner
1. Default currency per tenant (a tenant setting) or always ask per lead: recommendation: the amount field requires an explicit currency choice in S2, with a remembered last choice in the browser; a tenant default can follow with settings.
2. Should `WON`/`LOST` move the lead to a closed stage automatically? Recommendation: not in this slice; the status already tells it, and automatic moves interact with Bitrix24 stage sync (P2.8).
3. Is "Sales" the right default pipeline label? (shown through i18n, easy to change.)

## S1 status (API, 2026-11-12, branch `feat/p1-3-pipelines`, not merged/pushed/deployed)
Built as decided: migration `20261121090000_pipelines_and_opportunity` (expand, idempotent set-based backfill, switch, `pipelines` RLS last in the file, partial unique default index and an amount/currency CHECK as SQL), schema models `Pipeline`, `LeadStage.pipelineId`, `Lead.pipelineId`, composite FKs (stage must be in the lead's pipeline), opportunity columns; `ensureLeadStages` ensures the default pipeline and four coded stages; routes for pipelines, stage create/reorder/delete, stage move across pipelines (one update, audit `lead.pipeline.changed` with both pipelines), `PATCH /leads/:id/opportunity`, `lostReason` on the status route, owner cleared on deactivation (same transaction, audit `lead.owner_cleared`), list filters and additive fields (owners read in one batched query), `GET /leads/stages?pipelineId=`. Tests: unit (rules, grep test that nothing in `core/agent` reads lead money), integration (backfill re-run on the old shape inside a rolled-back transaction, CRUD and limits, FK at database level, validations, role matrix, RLS).

Deviations and decisions made while building:
- A second migration `20261121100000_leads_default_pipeline_on_demand` and a BEFORE INSERT trigger on `leads`: `pipeline_id` has a nil-UUID default in Prisma so existing code and tests that create leads without a pipeline keep working; the trigger fills it from the stage's pipeline or the tenant's default pipeline (created on demand).
- `pipelines.name` is nullable (default pipeline unnamed); on make-default the old default gets the stored name `Sales`.
- New pipelines are seeded with the four coded stages; only the coded stages of the *default* pipeline are protected (`STAGE_IS_DEFAULT`).
- Stage delete: a stage that holds leads is refused with `STAGE_HAS_LEADS` (not archived); an empty stage is hard-deleted. `lead_stages.archived_at` exists and is filtered on, but nothing sets it yet.
- The stage limit keeps the existing code `LEAD_STAGE_LIMIT` (web i18n exists); the limit is 20 active stages per pipeline.
- `amount` and `currency` must be sent together (both set or both null); amount as a number is `INVALID_BODY`. Clearing `lostReason` while LOST is `INVALID_VALUE`. `closeBefore`/`closeAfter` are inclusive. `source` filter is case-insensitive.
- Status route: `lostReason` is additive; `LOST` without it is 400 `LOST_REASON_REQUIRED`, a reason with another status is 400 `INVALID_BODY`.
- Not tested: running the migration against a populated production-sized database (only the backfill statements on the old shape inside a transaction).
