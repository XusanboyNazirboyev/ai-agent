# ADR 058 — A real sales funnel on the Leads page, and the AI agent staging leads (P1.3b)

Status: proposed by the reviewing agent on 2026-11-12 after the owner's request ("the funnel must be a real CRM funnel; the AI agent and the operator can both sort the lead"). Extends ADR 057 (pipelines, opportunity fields); revises its decision 5 sentence "`WON` and `LOST` do not move the stage automatically". Recommendations below are treated as accepted unless the owner answers otherwise.

## Context (read from the code on 2026-11-12)
- Today the "funnel" is four coded stages `NEW, HOT, WARM, COLD` (`lead-stage.util.ts`): they duplicate the lead **score**, so the board is a score list, not a sales process. Every lead is created in `NEW` and the agent never moves it afterwards; operators move it with a `<select>` on the card (no drag and drop, no column totals).
- The agent already scores deterministically (`core/leads/scoring.ts` + `lead.service.ts`): rule codes over signals `hasPhone`, `offerShown`, `quoteShown`, `intent`, collected slots; evidence only accumulates; an operator's score wins (`scoreSetByOperator`).
- Lead `status` (`NEW | IN_PROGRESS | WON | LOST`, with `lostReason`) is separate from the stage.

## Decisions
1. **Stages get a `kind`.** `lead_stages.kind` enum `OPEN | WON | LOST` (default `OPEN`). A pipeline has at least one `OPEN` stage; `WON` and `LOST` stages are the last columns ("closed"). Moving a lead into a `WON` stage sets `status = WON`; into a `LOST` stage sets `status = LOST` and requires a `lostReason` (same 400 `LOST_REASON_REQUIRED`); moving a `WON/LOST` lead back to an `OPEN` stage sets `status = IN_PROGRESS` and clears `lostReason`. One code path (`moveLeadToStage`) is used by the operator route, the agent and the status route, so stage and status never disagree.
2. **Default funnel for new tenants and new pipelines** (replaces `NEW/HOT/WARM/COLD`; the labels are i18n keys, tenants can rename/add/remove): `NEW` (new), `CONTACTED` (in conversation), `QUALIFIED`, `PROPOSAL` (offer/quote sent), `NEGOTIATION`, `WON` (kind WON), `LOST` (kind LOST). Existing tenants keep their stages unchanged (no data rewrite); the four old coded stages stay valid `OPEN` stages and their coded names keep their translations. The coded default stages of the default pipeline stay protected from deletion; the new coded set is created by `ensureCodedStages` only for pipelines that have no stages yet. HOT/WARM/COLD live on as the **score badge** on the card, never as columns for new tenants.
3. **The agent stages leads (rules first, never free LLM output; D4/D13).** After each scoring pass (`lead.service.ts`) a pure function `proposeStage(signals, stages)` returns a target stage code with reason codes: `NEW` at creation; `CONTACTED` once the customer sent a second message or the agent asked a question; `QUALIFIED` when the required slots are filled and a phone is known; `PROPOSAL` when an offer or a confirmed quote was shown (`offerShown`/`quoteShown`); `NEGOTIATION` when a handover to an operator is open on that conversation (the human has taken over). The agent only ever moves a lead **forward along open stages** and **only to coded stage codes that exist in the lead's pipeline** (a tenant that removed or renamed the structure simply gets fewer moves). It never moves a lead into `WON` or `LOST` and never moves backwards. The mapping lives in a locale-neutral core rule table (no vertical or CRM specifics in `core/**`).
4. **Operator wins, always.** `leads.stage_set_by` enum `AGENT | OPERATOR` (default `AGENT`) and `stage_set_at`. A manual move (drag, select, status route) sets `OPERATOR`; the agent never touches a lead whose stage was set by an operator. The operator can hand a lead back with a "let the AI sort this lead" action (sets `AGENT`; mirrors `scoreSetByOperator`).
5. **Per-pipeline switch.** `pipelines.ai_staging` enum `OFF | SUGGEST | AUTO`; default `AUTO` for new pipelines and `OFF` for existing tenants' pipelines (nothing changes on their boards until an OWNER/ADMIN opts in on the pipelines settings page). `SUGGEST` stores the proposal (`leads.suggested_stage_id` + reason codes) and the card shows "AI suggests: Qualified (phone collected, requirements filled)" with Accept/Dismiss; `AUTO` moves the lead. Agent moves use the same `moveLeadToStage` path with `actor = AGENT`.
6. **Every agent move is explainable and reversible.** An `audit_events` row `lead.stage.moved` with `{from, to, actor: 'AGENT', reasonCodes}` (no customer text), and the lead panel shows a "Stage history" list (who, when, why). The operator undoes a move by moving the card back (which locks it to the operator, decision 4).
7. **Board data the Kanban needs (one request, no N+1):** `GET /api/v1/pipelines/:id/board` -> `{ stages: [{ id, code, name, kind, position, count, totals: [{ currency, amount }] }] }` with per-stage counts and per-currency amount sums (decimal strings, computed in SQL, never summed as JS floats); the cards of a column keep loading with `GET /leads?pipelineId&stageId&cursor` (paged, 20 per page). A funnel summary strip (counts per stage and conversion `NEW -> WON` over the visible period) reads the same endpoint with an optional `?from=&to=` on lead creation date.
8. **Money stays operator data** (ADR 057 decision 6): the agent's staging rules read no amount; the grep test is extended to the staging module.

9. **Decision 9 (owner, 2026-11-12): one concept in the product.** Stage, score and status looked redundant to the owner. The funnel **stage** is the only thing operators set and see on a lead. (a) `status` is derived from the stage kind (OPEN -> NEW/IN_PROGRESS, WON, LOST) and is written only by `moveLeadToStage`; `PUT /leads/conversations/:id/status` and `/score` stay for API compatibility and the Bitrix sync but are **deprecated**, and the web stops using them. (b) `score` (HOT/WARM/COLD) stays an internal AI priority signal with reason codes; it is not operator-editable in the new UI and not a column; the board item keeps returning it read-only. (c) The status route calls `moveLeadToStage` (WON/LOST -> first stage of that kind in the lead's pipeline; none -> only the status is set, as before). (d) New pipelines never get the old NEW/HOT/WARM/COLD stages, only the 7-stage set.

## Web (Kilo, against this contract; supersedes the web section of ADR 057 S2)
Leads page redesign: pipeline switcher; a sticky filter bar (search, owner, tag, score, source, close date); funnel summary strip; Kanban with real drag and drop (pointer plus a keyboard path: focus a card, Space to pick up, arrows to move, Space to drop, announced to screen readers) and the stage `<select>` kept as the accessible fallback on the card; column headers with count and totals; terminal columns visually distinct (green/red) and collapsed by default on narrow screens; card = name, channel badge, amount, owner avatar, score badge, tags, "AI" mark when the stage was set by the agent, time since last activity; mobile (320px): one column at a time with a stage tab bar; a list view toggle. Dropping on a LOST column opens the reason dialog. The pipelines settings page gets the AI-staging switch and stage kind. i18n en/ru/uz-Latn, axe, 320px.

## Risks
Two sources of truth (status and stage) are reconciled by the single move path, and the migration must backfill nothing for existing leads (their stages are `OPEN`, their status is unchanged). Staging rules can look arbitrary to operators: reason codes are shown on the card and `AUTO` is opt-in for existing tenants. Drag and drop must not be the only way to move a card (a11y, mobile): the select and keyboard path stay. Per-currency totals mix nothing: one total per currency per column.

## Open decisions for the owner (recommendations above apply meanwhile)
1. Default stage names/count (7 stages above) and whether `NEGOTIATION` should exist by default.
2. `AUTO` as the default only for new pipelines, `OFF` for existing ones (recommended: yes).
3. Whether the agent may ever close leads as `LOST` after long inactivity (recommended: not in this slice; an operator-visible "stale lead" marker can follow).
