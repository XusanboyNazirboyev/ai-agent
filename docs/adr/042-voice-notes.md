# ADR 042: Customer voice notes (speech-to-text)

- **Status:** Accepted, 2026-11-07 (owner chose Gemini; provider stays off until Uzbek quality is measured).
- **Context:** Telegram voice notes were ignored (`unsupported`), so a customer who spoke got no answer. `docs/VOICE_READINESS.md` defined the port and policy and left the provider to the owner.

## Decision

- **Provider:** `gemini-3.5-transcribe` through the official SDK `@google/genai` 2.32.0 (`interactions.create`, inline audio, `transcription_config.language_codes` + `custom_vocabulary`, transcript in `output_text`). Docs read 2026-11-07: https://aistudio.google.com/docs/transcribe.md (Uzbek `uz-UZ` listed; OGG and Opus accepted), https://aistudio.google.com/docs/audio.md, https://aistudio.google.com/docs/pricing.md (about $0.005 per minute; paid tier content is not used to improve products). `STT_PROVIDER=none` (default) or `gemini` with `STT_API_KEY` (a paid-tier key).
- **Intake:** a Telegram voice note (Bot API `Voice`, read 2026-11-07) is stored as a `VOICE` message with empty text, `voice_status=PENDING`, `media_ref` = file_id, mime type and duration (additive migration `20261111090000_voice_messages`). A malformed voice object is ignored, never fatal to the update.
- **Worker:** before the agent runs, `VoiceTranscriptionService` checks the voice policy (type, length) before downloading, downloads with `getFile` (link holds the bot token: never logged; at most 5 MB by policy, 20 MB by Telegram), checks the size, transcribes, and stores `TRANSCRIBED` with the transcript as the message text or `FAILED` with an empty text.
- **Agent:** a transcript is ordinary untrusted customer text. A batch whose only content is a failed note is answered by code without a model call: "please type" (`voiceNotUnderstood`), and after a second failed note in a row a handover (`VOICE_UNREADABLE`). The echo (agent OFF) sends nothing for an empty batch.
- **Inbox:** a voice note shows "🎤 Voice message (transcript)", "transcribing…" or "could not be understood".
- **Not done:** echoing the transcript back to the customer ("I heard: …") — digits in a transcript would trip the fact guardrail (D5); Instagram and Messenger audio attachments (their payload shape is not verified yet).

## Amendment 2026-11-09: metering (audit REV-03)

- Before audio leaves the server, the worst case (`STT_WORST_CASE_USD_PER_MINUTE`, default $0.02/min, 4x the pricing page's own ~$0.005/min estimate) is reserved on the same ledger as model calls (tenant monthly cap `LLM_TENANT_MONTHLY_BUDGET_USD`, conversation cap `LLM_CONVERSATION_BUDGET_USD`). A refused reservation means no provider call: the note is FAILED (`BUDGET_EXHAUSTED`) and the customer is asked to type.
- Spend is the provider-reported tokens at the paid-tier prices of https://aistudio.google.com/docs/pricing.md read 2026-11-09: input (audio) $2.00, output (text, including thinking) $12.00 per 1M tokens; thought tokens are billed as output. The record is an `llm_usage_records` row with purpose `transcribe` and turn key `voice:<messageId>`. Without reported usage, or on a timeout or error, the worst case stays counted (reservation UNKNOWN).
- REV-01, owner decision 2026-11-09: voice notes are transcribed also when the account's agent mode is OFF, so operators can read them without listening; this is the current behaviour, and the budget metering above still applies.

## Amendment 2026-11-09: first measurement on the owner's recordings (the "before enabling `gemini`" step)

Owner priority (fifth decision, 2026-11-09): speech to text of voice notes comes first; replies stay text (voice replies and calls are paused, ADR 045). Measured with `scripts/stt-compare.ts` through the production `SpeechToText` adapters on the owner's 9 Telegram voice notes (OGG, 32 s of audio, one speaker, quiet room; exact words written by the owner; 54 reference words: 38 uz-Latn, 5 uz-Cyrl, 11 ru). One run per mode unless stated; the corpus WER counts words after folding apostrophes and, for Uzbek, after transliterating both sides to Latin.

| ------------------------------------------------------------- | --------- | ------- | ------------ | --------------- | --------------------------------------------------------------------- |
| `gemini-3.5-transcribe`, languages uz/ru/en offered (default) | 35-37%    | 47%     | 9-18%        | 2.7-2.9 s       | two runs: 19/54 and 20/54 errors; always Latin for Uzbek; no failures |

- **Decision:** keep Gemini (ADR 042's choice) with the default configuration as the voice-note provider; no vocabulary or language narrowing for now. The ElevenLabs file adapter (`src/speech/elevenlabs-speech-to-text.ts`, tested with a fake transport) stays in the code, **not wired**: automatic language detection is not safe for Uzbek, and it has no token pricing (billed by audio time), so metering would keep the worst case counted.
- **Caveats (do not read these as a production WER):** one speaker, 9 short clips, 54 words; run-to-run variation exists (±1 word). On lines 3, 4 and 8 all providers agree with each other and not with the written words (e.g. all say "…keyin ham dars bo'ladimi?" for the written "…dars bormi?"), and the owner confirmed (2026-11-09) that the written words are exactly what was said: this is a recognition error all models share (they replace the spoken words with a more common phrasing), so the figures above stand as measured. On line 5 (a spoken phone number) the providers disagree with each other and with the written digits: digits from speech are the least reliable part. Noise, accents, longer clips and mixed Uzbek/Russian sentences were not tested. A native-speaker review is still required for the "stable" label (D18).
- **Seen:** every Uzbek transcript came back in Latin script, also for the line written in Cyrillic (the speech has no script). Whether a Cyrillic-writing customer who sends a voice note should get a Cyrillic reply is a policy question (D17), open.
- **Cost of the measurement** (estimates from the pricing pages, not from billing): about 3 minutes of Gemini audio (about $0.02) and about 4 minutes of ElevenLabs audio.
- **Open and blocking enabling for a tenant:** (1) a transcript is used as ordinary customer text; `decideVoice` computes `needsConfirmation` (always true: Gemini reports no confidence) but nothing uses it, so a misheard phone number or date goes straight to the agent. Owner decision needed: confirm what was understood (echo the transcript, which D5 allows only if digits are handled), or never take phone numbers and dates from speech without a typed confirmation, or accept the risk. (2) Staging needs `STT_PROVIDER=gemini` and `STT_API_KEY` (a paid-tier key) in its environment; the local `.env` has neither. (3) Instagram and Messenger audio are still not handled.

## Amendment 2026-11-09: digits heard by a machine are not a phone number (owner chose this work)

Owner, the same day: no calls; only voice notes are answered, in text. Of the open item "(1) misheard digits", the owner picked the safe direction; the exact variant stays configurable:

- `VOICE_DIGITS_POLICY` = `typed` (default) | `accept`. With `typed`, a phone number is taken only from text the customer typed: when the answered batch contains a voice-note transcript (`voice_status = TRANSCRIBED`), neither the contact phone capture (Telegram pipeline) nor the booking flow (`ActionService.turnContext`) reads a number from it; the booking flow then asks for the phone again (`phoneRequest`), and the typed number is used. This matters because a stored phone is never replaced (`capturePhone` writes only when the contact has none), so a misheard first number would have stayed. Any value other than an explicit `accept` behaves as `typed` (fail safe). `accept` restores the earlier behaviour.
- Not changed: dates, times and bookings already go through a proposal the customer must confirm exactly (ADR 024/046), so a misheard date is shown back before anything is booked. The agent may still repeat a number from a transcript in its own reply only through the normal guardrail (a number the customer "said" counts as customer text).
- Not built: echoing the transcript ("I heard: …") to the customer; a dedicated "please type the number" message on the voice turn itself (the booking flow re-asks; a lead without an action just has no phone yet). Instagram/Messenger voice notes are not handled at all yet.
- Tests: unit (`leads/phone.spec.ts`, including the fail-safe), integration (`telegram-agent.integration.spec.ts`: a heard number is not stored, the typed one is, `accept` stores it; `action-pipeline.integration.spec.ts`: no proposal from a heard number, the phone is asked again, the typed number makes the proposal; checked by disabling the guard, which makes it fail).

## Amendment 2026-11-10: Instagram voice messages

Owner: Instagram next. Built to the documented webhook shape and tested with a fake Meta; **not verified against a real Instagram voice message** (no account is connected for a real Meta check yet), so the three things the docs do not say are handled defensively, not assumed.

- **Documented** (Meta "Webhook Notification Examples", read 2026-11-10): a `messages` notification carries `message.attachments[] { type, payload { url } }`; `audio` is a supported type; `is_unsupported: true` marks unsupported media. **Not documented:** that an in-app voice message arrives as `audio`; how long the URL lives; whether it needs a token; the container; the duration. Sending docs list "aac, m4a, wav, mp4" up to 25 MB for outbound audio, which is not evidence for inbound.
- **Intake:** a message without text but with an `audio` attachment (first one, URL a string of at most 2,000 characters) becomes a `VOICE` message, `voice_status=PENDING`, `media_ref` = the URL; text with an attachment stays a text message; echoes are ignored as before. Applies to `accept()`, which Messenger shares, but only the Instagram normalizer produces voice events.
- **Fetch (worker, before the agent runs):** `downloadPublicMedia` treats the URL as untrusted input: https on the default port only, no embedded credentials, STRICT outbound policy, DNS pinned to public addresses (no rebinding), no redirects, **no credentials of ours sent**, at most 2 MiB (declared and actual), 10 s deadline. Any failure means `FAILED` and the customer is asked to type; the URL and body are never logged.
- **Format and length:** the response media type decides (`audio/x-m4a` and `audio/m4a` are sent as `audio/mp4`); a missing or unknown type is not sent to any provider (no guessing). `audio/aac` was added to the allowed types. The duration is unknown, so the policy maximum (60 s) is both the check and the metering worst case; the 2 MiB bound limits what can arrive. If Gemini rejects a container, the ElevenLabs backup (which accepts all major formats) answers.
- **Same rules as Telegram:** transcript = untrusted customer text; the digits policy applies (`fromSpeech`); STT none = "please type"; two failed notes in a row = handover; metering as before.
- **To verify with the first real voice message:** that the type is `audio`; the media type of the response; whether the download needs no token (if it does, the note fails safe to "please type" and this amendment must change); how long the URL stays valid (we fetch immediately; a retried job after expiry also fails safe).
- **Tests:** unit (normalizer, downloader including SSRF cases, checked by loosening the policy, media types) and integration on the real database with a fake Meta transport, fake download and fake STT (stored as PENDING, transcribed and answered through Instagram, download failure, unknown media type, STT not configured).
- **Side fix:** `dev-superadmin.integration.spec.ts` counted operators by display name, which a later test in the same file changes in the shared database, so it failed on every second run; it now counts the account by its e-mail. Integration suite: 566/566.

## Amendment 2026-11-10 (later): Instagram voice verified with the first real message

The owner sent a real Instagram voice message to the staging account; it failed (twice, then a `VOICE_UNREADABLE` handover) and the staging logs, database row and a probe from the server gave the facts the 2026-11-10 amendment listed as unverified:

- **Type:** the webhook delivered it as an `audio` attachment (stored as `VOICE`/`PENDING`); host `lookaside.fbsbx.com`, URL about 300 characters, https.
- **Token:** none needed; a plain GET from the server answered `200` with the bytes (about 20 KB for a few seconds).
- **Container:** the response said `Content-Type: video/mp4`, `Content-Disposition: inline;filename=audioclip-<ms>-<n>.ogg`, and the bytes were **Ogg/Opus**, mono, 48 kHz. So the declared type is wrong for voice messages.
- **Redirect without a User-Agent:** a request with no `User-Agent` header (what our HTTP client sent) gets a `302`; any `User-Agent` gets the `200`. The downloader refuses redirects by design, so it failed as `HTTP_ERROR`, which the service then logged as `PROVIDER_ERROR`.
- **URL lifetime:** still unknown (the probe ran about 20 minutes after delivery and worked; no later check).

Changes: the downloader sends `User-Agent: tezda-media-fetch/1.0` (an honest product name, not a browser string; redirects are still refused); the container is decided from the first bytes (`sniffAudioContainer`: Ogg, WAVE, MP4/M4A, MP3 and ADTS AAC only) and the declared type is used only when the bytes are not recognised **and** it is itself a known audio type, otherwise the clip is refused; the failure log now carries the specific download code (`DOWNLOAD_HTTP_ERROR` etc.), never the URL. Tests: unit for the sniffer and the header, integration for "Ogg labelled `video/mp4` is transcribed as `audio/ogg`" and "`video/mp4` with non-audio bytes is refused"; both checked by removing the fix.


## Amendment 2026-11-21: Groq first, and voice replies (owner)
- **STT order:** `STT_PROVIDER=groq` uses Groq `whisper-large-v3` (existing `WhisperSpeechToText`, `https://api.groq.com/openai/v1/audio/transcriptions`, docs read 2026-11-21: ogg accepted, 25 MB free tier). Uzbek is not on Groq's language list, so a Groq error, timeout or empty result goes on to `gemini-3.5-transcribe`, then ElevenLabs Scribe (`uz-Latn` hint). `gemini` keeps the old order.
- **Voice replies:** `VOICE_REPLIES=elevenlabs` with `VOICE_REPLY_VOICE_ID`. After a bot text reply is delivered on Telegram, a customer whose last message was a voice note also gets the same text as speech: ElevenLabs `POST /v1/text-to-dialogue` (`eleven_v4_turbo`, `language_code` from the conversation, MP3; docs read 2026-11-21), sent with Bot API `sendVoice` (MP3 accepted, 50 MB). The text stays, so checked prices and dates remain readable. Best effort: a failure (quota, network, Telegram) leaves the text alone; once per reply (the send step claims the message first). Operator messages are not spoken; Instagram not yet.
- **Plan limits (checked 2026-11-21 with the owner's key):** the account is on ElevenLabs' free tier, 10,000 characters a month (798 used). Free users cannot use library voices through the API, which includes all six Uzbek voices in the account (Davronbek, Shohjahon, Firdavs Urinov, Dilzoda, Farruh, Mirzaev); a premade voice (Sarah) produced an Uzbek MP3. `eleven_v3` refuses `language_code=uz`.
- **Gemini free-tier key:** not wired. Google's pricing page (read 2026-11-20) says free-tier content is used to improve its products, and its low rate limits would turn eval runs into false failures; no customer path uses it.
- **Gemini TTS first (owner 2026-11-21, later the same day):** `VOICE_REPLIES=gemini` speaks the reply with `gemini-3.8-flash-lite-tts` (voice `Kore`; Northern Uzbek is supported; $0.0015 per 10 s of audio in 2026, $0.003 from 2027; docs read 2026-11-21: speech-generation and pricing pages) on the paid `GEMINI_API_KEY` (the free tier may use content to improve Google's products, so its daily quota is not used for customers). The unary answer is a WAV, so the api image now has ffmpeg (`apk add ffmpeg`) to turn it into OGG/Opus for `sendVoice`. When Gemini gives no audio, ElevenLabs (premade voice Sarah, free plan) answers; when both fail, only the text is sent. Verified 2026-11-21 with the project key: an Uzbek sentence returned a WAV and became a 22 KB OGG/Opus.

- **NeuronAI native Uzbek voice first (owner 2026-11-21, later still):** `VOICE_REPLIES=neuronai` with `NEURONAI_API_KEY` speaks Uzbek replies with NeuronAI's stock voice `NEURONAI_TTS_VOICE` (`kamola` by default, `muhriddin` the male voice the owner also named; `madina`, `saodat`, `kamron` allowed). Docs read 2026-11-21 (https://docs.neuronai.uz/api/openapi.json): `POST https://my.neuronai.uz/api/v1/tts/synthesize`, Bearer key, JSON `{text, voice_id, language: "uz", quality: "standard"}`, answer `audio/wav`; 0.3 credits per character with 1 credit = 1 UZS (https://docs.neuronai.uz/platform/billing). Verified 2026-11-21 with the project key: a 112-character Uzbek sentence took 0.7 to 0.9 s and cost 33.6 credits per voice (24 kHz mono WAV). A reply in another language, or a NeuronAI failure, goes to Gemini (when `GEMINI_API_KEY` is set), then ElevenLabs.
- **Deepgram Nova-3 first for speech-to-text (owner 2026-11-21, later still):** `STT_PROVIDER=deepgram` with `DEEPGRAM_API_KEY`. Docs read 2026-11-21: Nova-3 monolingual lists Uzbek (`uz`); language detection cannot be limited to `uz` (a `detect_language=uz` list is refused) and unrestricted detection labelled our Uzbek sample Turkish; `mip_opt_out=true` keeps audio only while the request runs; about $0.0048 per minute. Measured with the project key on known Uzbek text (NeuronAI voices, clean and with added noise, WAV and OGG/Opus): Deepgram word for word at confidence 0.96 to 1.0, Groq Whisper with spelling errors ("malumat", "xaftasige", "kulay"); Russian and English forced to `uz` scored 0.69 and 0.73. So Deepgram is called with `language=uz`, and a transcript under 0.8 confidence is `UNSUPPORTED_LANGUAGE`, which (with errors, timeouts and silence) goes to Groq with no language hint so it detects Russian or English itself, then to the Gemini chain. Real customer notes are not yet measured: the 0.8 bar may send some dialect speech to Groq.
- **OvozAI first for speech-to-text (owner 2026-11-21, last):** `STT_PROVIDER=ovozai` with `OVOZAI_API_KEY`. Docs read 2026-11-21 (https://api.ovozai.uz/docs.md, https://api.ovozai.uz/privacy): OpenAI-compatible `POST https://api.ovozai.uz/v1/audio/transcriptions` (model `ovozai-transcribe`, Bearer key, multipart `file`, answer `{text, duration, credits}`), built for Uzbek and mixed Russian/English, 1 credit per second (no speech and failures free), 120 requests a minute and only 2 transcriptions at a time per account; API recordings are deleted once processed and never used for training, transcripts kept 7 days. Measured with the project key on the same samples: every one word for word (clean and noisy Uzbek, where Deepgram wrote "Yurtimiz" for "Kursimiz" on the noisy one, plus Russian and English detected by itself) in 2.3 to 2.9 s. It reuses the Whisper adapter. An error (the busy 429 included) or a timeout goes to the Deepgram chain with no language hint; silence keeps its verdict.
- **Voice replies on Instagram (owner 2026-11-23):** the same rule as Telegram (this turn sent a voice note or asked for voice in text; otherwise text only) and the same budget caps. Docs read 2026-11-23 (https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/messaging-api): an audio message is `message.attachment {type: "audio", payload: {url}}`; audio formats aac, m4a, wav, mp4, at most 25 MB. Meta fetches the URL, so the spoken reply is turned into ADTS AAC (ffmpeg; an .m4a needs a seekable output), kept in Redis for 10 minutes under a 192-bit random token, and served at `GET /webhooks/instagram/voice/<token>.aac` (under `/webhooks/*` because only that path reaches the api through Caddy). Nothing is synthesized when `PUBLIC_BASE_URL` or the store is missing. Not verified yet: Meta fetching the URL from staging and the Instagram app playing ADTS AAC (owner retest).
