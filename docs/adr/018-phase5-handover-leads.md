# ADR 018: Phase 5 operator handover, leads, offers shown, STUCK

- **Status:** Accepted (branch `phase5/handover-leads`, not yet merged)
- **Date:** 2026-10-24

## Context
Phase 4 ended in a typed handover outcome plus a stored `Handover` row; nobody was notified, operators had no commands, leads were not created, shown offers were not recorded and the STUCK trigger did not exist. The Prisma schema already had `Lead`, `Quote`, `Handover`, `Operator`, `AuditEvent` and the four conversation states.

## Decisions
- **Ownership is a pure state machine** (`core/handover/state-machine.ts`): `BOT_ACTIVE -HANDOVER-> WAITING_OPERATOR -TAKE_OVER-> OPERATOR_ACTIVE -RETURN_TO_BOT-> BOT_ACTIVE`, `CLOSE` from any open state, `REOPEN` when a customer writes to a `CLOSED` conversation. `HandoverService` applies it in one short transaction per command under the per-conversation advisory lock the pipeline already uses, with a version compare-and-set. The bot's commit step already discards a reply when state or version changed, so a bot reply and an operator take-over cannot both win.
- **Commands** (take over, reply, return to bot, close, note) are tenant-scoped, authorize an active `OWNER/ADMIN/OPERATOR` of the tenant, are idempotent through a unique partial index on `audit_events (tenant, action, idempotency_key)`, and write an audit row. Competing take-overs: exactly one wins (tested from two connections). Replies are written as `OPERATOR` messages and sent through the normal `telegram.send` outbox path.
- **`OperatorNotifier` port** with `TelegramGroupNotifier` (Bot API: `sendMessage` with `reply_markup`/`reply_parameters`, `answerCallbackQuery`, `editMessageReplyMarkup`; checked against core.telegram.org/bots/api on 2026-10-24, including `callback_data` 1 to 64 bytes). The operator group is `channel_accounts.operator_chat_id`. The card carries a `ref:<handover id>` line; an operator's reply to any handover message is routed by that reference, verified against the tenant and the stored chat. Customer follow-ups while operators own the conversation are forwarded threaded under the card. A handover is `SENT` only after Telegram accepted the card; no chat or a rejected chat gives `FAILED` with a code; transient errors retry through the queue and end in `FAILED retries_exhausted`. Operator wording (en/ru/uz-Latn) is beta and unreviewed.
- **SLA**: `slaDueAt` is set at creation (`HANDOVER_SLA_MINUTES`); a periodic scan marks an overdue `OPEN` handover once (compare-and-set), queues one alert, and, only if operators were reached, one customer notice (`operatorDelayNotice`, no time or reply promised).
- **Leads are local-first.** `Lead` is written in the commit transaction; scoring is deterministic from the pack's `leadScoring` rules, reason codes always stored, evidence only accumulates; one lead per conversation. CRM sync is a queued, separate step: no `createLead` capability -> `NOT_REQUIRED` (never SYNCED); failure -> `FAILED` with code, attempts and a backoff, retried by the periodic scan up to 8 attempts; the local row is never lost. No LLM classification is used. A phone number is stored only when the customer typed one (conservative parser); the phone request is a fixed template appended at most once, after facts were delivered.
- **Offers shown** (`shown_offers`) are written only after Telegram accepted the message (delivery state `SENT`), from the committed turn's verified facts restricted to the fact ids in the reply. A `Quote` row is written only for a live confirmed quote whose offer exists in the synced catalog (its foreign key); otherwise the reason is stored (`OFFER_NOT_SYNCED`, `NOT_A_CONFIRMED_QUOTE`). Idempotent per message and offer.
- **STUCK** (`core/agent/stuck.ts`): needs `STUCK_REPEAT_LIMIT` (default 2) earlier no-progress turns; any new slot or answered turn resets it. Fires on the same question asked again, or the same normalized customer text repeated, with no new slot. Per-turn signals (`asked_slot`, `slots_filled`, `text_fingerprint`) are stored, not raw text. It runs in the agent core, never in the router.

## Not done / limits
- `HIGH_VALUE` and `LEGAL_UNVERIFIED` triggers (need pack thresholds and Phase 6 knowledge). Morning digest and follow-ups (Phase 6). HTTP command API with RBAC and the web inbox (Phase 6A); today operators act from the Telegram group only.
- **No real Telegram call was made**: the notifier is tested with a mocked transport and a fake notifier. The webhook must be registered with `allowed_updates` including `callback_query`, and the bot must be in the operator group (privacy-mode behavior for group replies was not verified).
- An ambiguous Telegram send of a card can produce a duplicate card on retry.
- Quote rows depend on catalog sync having stored the offer.
