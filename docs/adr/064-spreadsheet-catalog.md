# ADR 064 — Catalog from a price-list spreadsheet (first pilot: tourism)

Status: proposed on 2026-11-14 after the owner chose tourism for the first pilot and asked for research and a start. Builds on ADR 007 (connector contract), 059 (connector roles), D1/D5 (facts only from tools, rendered by code), D10 (live check before showing a price).

## Context
The agent answers prices, dates and availability only from a connector (`searchItems`, `getQuote`, `checkAvailability`, called live from `core/agent/tools.ts`). Staging uses the fictional `mock` connector; Bitrix24 is lead-sink only. A tour agency keeps its prices in Excel or Google Sheets and has no API, so today the agent cannot quote its tours and hands every price question over (`NO_DATA`).

**Research (2026-11-14, web search; thin).** No real price list of an Uzbekistan operator was found. General sources agree on the shape of a package price list: destination or hotel, hotel category, number of nights, meal plan (BB breakfast, HB half board, FB full board, AI all inclusive), room type (SGL single, DBL double, TRPL triple), **price per person**, departure date, flight and what is excluded (insurance, visa, personal expenses). CIS operator tables list one row per check-in date and nights with columns per meal and room type, prices in USD or the local currency. A seat count per departure was not found as a standard column in public templates; agencies usually know it from their own allotment. Sources: [Holidify agent guidelines](https://agents.holidify.com/post/create-high-quality-tour-package), [costing guide](https://www.linkedin.com/pulse/demystifying-art-tour-package-costing-guide-beginners-bhanu-prakash), [magput.ru price list PDF](https://magput.ru/files/programs/programPriceList/a729768e-5e64-45a3-bdf7-5c8ada34e777.pdf), [Sletat provider API meal codes](https://wiki.sletat.ru/w/Sletat_Ru_Provider_API). The columns of the real agency are unknown until it sends its file, so the design must not hard-code a layout. The sample in `docs/samples/tourism-price-list.sample.csv` is invented, not a real price list.

## Decisions
1. **A `spreadsheet` connector, DB-backed.** It advertises `search`, `liveQuote`, `availability` (no write capabilities, no `sync`) and answers from the tenant's uploaded rows. It binds to the `CATALOG` role like any connector (ADR 059). Nothing in the agent core changes.
2. **Mapping instead of a fixed template.** The admin uploads a file; the system reads the header, **suggests** a mapping from the columns to the canonical fields (synonyms in en, ru, uz-Latn: "Hotel / Отель / Mehmonxona", "Price / Цена / Narx", ...), the admin confirms or fixes it, and sees a preview with row-level errors before saving.
3. **Canonical mapping.** One row becomes one *offer* (a departure) of one *item* (the package): item title is composed from destination, hotel and nights (or taken from a column); `itemType = tour`; offer `startsAt` from the departure date, `price` with `currency`, `pricingBasis = PER_PERSON` unless a column says otherwise, `seatsLeft`, availability from seats (0 = `SOLD_OUT`, at most a configurable threshold = `LIMITED`, more = `AVAILABLE`, no seat column = `UNKNOWN`). Everything else (hotel, stars, nights, meal plan, room type, departure city, flight, notes) goes to `attributes` as typed text. The row key is a code column or a hash of the identifying columns, so a re-upload updates the same offer.
4. **Prices are never guessed.** A row with a missing or non-numeric price, an unreadable date or an unknown currency is rejected with its line number and reason and not stored; the admin sees the list. Numbers accept `1 250`, `1,250.50`, `1250,5` and a leading currency symbol; dates accept `2026-03-14`, `14.03.2026`, `14/03/2026` (day first, stated in the UI); an ambiguous or impossible date is an error.
5. **Freshness is a fact too.** Every upload stamps `uploaded_at`; offers carry `validUntil = uploaded_at + freshness days` (tenant setting, default 3). After it, availability reads `UNKNOWN` and a quote is refused, so the agent hands over instead of quoting a stale price. The UI shows "prices updated 2 days ago" and warns when they are stale.
6. **Upload replaces, with a preview.** A new upload for the same catalog replaces its rows in one transaction (offers missing from the new file are removed); the preview states how many rows are added, changed and removed. The previous version is kept as one version back for undo.
7. **Formats in order.** S1 CSV (Excel and Google Sheets both export it; comma, semicolon or tab; UTF-8 with or without BOM). S3 `.xlsx` (needs a parser dependency: a supply-chain review and an ADR amendment first; the project rule is no new dependency without a reason) and a Google Sheets link (read-only, needs Google access, later). Grid layouts (dates as rows, meal and room as columns) are an S3 "unpivot" step; S1 expects one offer per row and says so.
8. **Security.** Uploaded cells are untrusted text (D8): length limits per cell and per file (for example 5 MB and 20 000 rows), no formulas evaluated (CSV is text), values never reach a prompt except through the fact pipeline, `attributes` keys come from the mapping, not from the file. Per-tenant tables with `tenant_id`; upload and mapping routes OWNER and ADMIN, audit `catalog.sheet.uploaded` (counts only, no cell text).
9. **Storage.** `sheet_catalogs` (tenant, name, mapping, freshness days, uploaded_at, row counts, active version) and `sheet_catalog_rows` (tenant, catalog, row key, canonical item and offer JSON, normalized title for search, starts_at, price). Additive migration, tenant-scoped, covered by the RLS work later.

## Staging of the work
- **S1a pure core (no DB):** CSV reader, header-to-field suggestion, row mapper with number, date, currency and meal-code normalisation, row errors. Unit tests with the sample file.
- **S1b storage and connector:** tables, import service (replace in a transaction, freshness), `SpreadsheetConnector`, registration, upload and preview API, role binding, integration tests (agent gets a verified quote from an uploaded row, a stale sheet hands over, a bad row is rejected, tenant isolation).
- **S2 web:** upload, mapping screen with suggestions and preview, freshness banner, "replace file".
- **S3** `.xlsx`, grid unpivot, Google Sheets link.
- **S4** tourism template: pipeline stages, fields (destination, dates, travellers, budget), tags, travel-pack wiring.

## Open questions for the owner and the pilot agency
1. The agency's real file (any layout, prices may be made up): columns, whether one tour has several departure dates, per-person or per-room prices, child and infant prices.
2. Seats: does the agency know seats left per departure, or only "available / sold out"?
3. Freshness: how often will the file be re-uploaded? (sets the default of 3 days)
4. Currency: USD, UZS or both in one file?

## Risks
A wrong mapping silently turns a column into a price: mitigated by the mandatory preview with a sample of mapped rows and by rejecting rows rather than guessing. A stale file quoting old prices: mitigated by decision 5. Grid-shaped files do not import in S1: the preview says so plainly.
